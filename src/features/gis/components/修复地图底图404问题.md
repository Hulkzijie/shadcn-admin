**Assistant**

我先确认生产环境的表现，结论是：站点 nginx 里根本没有 `/map`、`/anno` 这两个反代规则（`/java-api`、`/py-api` 都在，SPA 回退也正常），所以请求落到了静态站点，返回 404。另外你 `.env` 里的 tk 是「浏览器端」类型，服务端直连会被天地图拒绝（我实测返回 `301012 权限类型错误`），必须换成「服务端」类型的 tk。

现状的 [tianditu-tiles.conf](file:///Users/wangzijie/Documents/wx/wisecloud-admin/deploy/tianditu-tiles.conf) 写成了独立 `server { server_name map.example.com; listen 80; }`，不能直接用在 www.wisecloud.si 上。我把它改成「http 段缓存声明 + server 段 include」两份。

配置已拆成两份，放到服务器上即可（前端不用改，打包产物里已经是 `/map/{z}/{x}/{y}.png`）。

## 1. 申请服务端 tk
[天地图控制台](https://console.tianditu.gov.cn) → 应用管理 → 新建 key 时**应用类型选「服务端」**（现有的 `bd67b1c...` 是浏览器端，服务端调用会返回 `301012 权限类型错误`）。若填了 IP 白名单，加上服务器出口 IP。

## 2. 上传两份配置

```bash
sudo mkdir -p /var/cache/nginx/tianditu /etc/nginx/snippets
sudo chown -R www-data:www-data /var/cache/nginx/tianditu   # worker 用户是 nginx 则改 nginx

sudo cp deploy/tianditu-cache.conf /etc/nginx/conf.d/tianditu-cache.conf
sudo cp deploy/tianditu-tiles.conf /etc/nginx/snippets/tianditu-tiles.conf
sudo sed -i 's/__TK__/你的服务端tk/g' /etc/nginx/snippets/tianditu-tiles.conf
```

## 3. 在现有站点 server 块里 include

找到 www.wisecloud.si 的 `server { listen 443 ssl; ... }`（就是已经有 `/java-api`、`/py-api` 的那个），加一行：

```nginx
server {
    listen 443 ssl;
    server_name www.wisecloud.si;
    # ... 现有 ssl / root / java-api / py-api 配置 ...

    include /etc/nginx/snippets/tianditu-tiles.conf;

    location / {
        try_files $uri $uri/ /index.html;
    }
}
```

注意两点：
- 不要像旧版那样单独写 `server { server_name map.example.com; listen 80; }`，这个域名不存在，请求永远到不了。
- `location ~ ^/map/...` 是正则 location，优先级高于 `location /` 的 SPA 回退，不会被打到 `index.html`。

## 4. 生效与验证

```bash
sudo nginx -t && sudo nginx -s reload

curl -I https://www.wisecloud.si/anno/4/13/6.png
# 期望：HTTP/2 200 + content-type: image/png + x-cache-status: MISS（再请求一次变成 HIT）
```

## 5. 清 Cloudflare 缓存（关键）

现在线上这两个路径的 404 被 Cloudflare 缓存了（`cf-cache-status: HIT`、`max-age=14400`），不改会一直返回 404。去 Cloudflare 控制台 → Caching → Configuration → **Purge Everything**；再在 Cache Rules 里对 `/map/*` 和 `/anno/*` 设置 **Bypass cache**（源站 nginx 已缓存 30 天，边缘不必再缓存，也能避免再被 404 污染）。

现在是什么问题  在vite.config.ts 中有anno 和map

**Assistant**

核心原因：**`vite.config.ts` 里的 `server.proxy` 只在 `vite dev` 本地开发服务器上生效，打包后完全不存在。**

具体链路：

1. 本地开发：浏览器请求同源 `/anno/4/13/6.png` → Vite dev server 命中 [vite.config.ts](file:///Users/wangzijie/Documents/wx/wisecloud-admin/vite.config.ts#L26-L39) 的 `'/anno'` 代理 → 重写成天地图 WMTS 地址 → 正常返回瓦片。
2. 生产构建：`vite build` 只产出纯静态文件，**代理配置不会被打包进去**；产物里只留下 `VITE_MAP_LABEL_TILE_URL=/anno/{z}/{x}/{y}.png` 这个相对路径（见 [gis-map.tsx](file:///Users/wangzijie/Documents/wx/wisecloud-admin/src/features/gis/components/gis-map.tsx#L52-L61)）。
3. 上线后：浏览器请求 `https://www.wisecloud.si/anno/4/13/6.png` → 打到线上 nginx/Cloudflare，线上没有任何规则把 `/anno`、`/map` 转到天地图（只有 `/java-api`、`/py-api`）→ 落到静态目录找不到该 png → 404。

也就是说：`/map`、`/anno` 这套「同源路径」只是前端约定，**开发环境由 Vite 实现，生产环境必须由 nginx 实现同一套约定**，两边不能只做一半。

另外提醒两点：

- [tianditu-tiles.conf](file:///Users/wangzijie/Documents/wx/wisecloud-admin/deploy/tianditu-tiles.conf#L31-L76) 现在是独立的 `server { listen 80; server_name map.example.com; }`，这个域名不存在，整块放进 conf.d 对 wisecloud.si 无效。真正生效需要把两个 `location ~ ^/(map|anno)/...` 挪进 www.wisecloud.si 的那个 `server { listen 443 ssl; }` 里（或写成 snippet 后 `include`）。
- 那个文件里的 `__TK__` 必须换成「服务端」类型 tk，浏览器端 tk 服务端直连会返回 `301012 权限类型错误`。

云端 404 还被 Cloudflare 缓存了，改完 nginx 后要 Purge Cache，否则仍会看到 404。

需要的话我可以直接改好后端配置版本（snippet 形式 + include 示例）。

## 三个结论

1. **前端基本不用大改**：maplibre + ReactFlow + Zustand + Query 已经覆盖目标栈 90%，只差「绘制编辑」（terra-draw）和「剖面图」（ECharts）。真正的工作量在后端。
2. **核心是补三块后端能力**：PostGIS（空间分析）、GraphHopper（路网/路线规划）、Python 服务（GDAL/地形/AI）。你已有 `/py-api` 这个入口，正好承载第 3 块。
3. **AI 规划路线的链路**= FastAPI 收自然语言 → LangGraph/Ollama 解析成路点 → GraphHopper `/route` 算路 → 返回 GeoJSON → maplibre 渲染。这条路不需要天地图，也不受地域封锁。

## 这套方案成立的前提

| 项 | 约定 |
|---|---|
| 数据契约 | 后端只出 `FeatureCollection`（WGS84 / EPSG:4326），两边各自投影到 3857 显示 |
| 编辑产物 | 编辑页保存时调现有 `createFeature` / `updateFeature`（[api.ts](file:///Users/wangzijie/Documents/wx/wisecloud-admin/src/features/gis/api.ts#L114-L130)），不走本地状态 |
| 底图 | 只用一套瓦片模板（同一个 `VITE_MAP_TILE_URL`），OL 用 `ol/source/XYZ`，maplibre 用 raster source，别再维护两套底图配置 |
| 校验 | **几何校验放后端**（shapely / PostGIS：自相交、闭合、最小面积、跨图层拓扑），前端只做即时提示。两套前端各写一遍校验必然不一致 |

## 要接受的成本

1. **两套图层加载逻辑**：同一个业务图层，OL 是 `VectorSource + WFS/WMTS`，maplibre 是 `geojson source + layer`，配置和样式都要写两遍（样式可以用同一份配色 token 生成，但代码是两份）。
2. **两套交互**：点击拾取、hover 高亮、弹窗定位，两边实现不同。
3. **两套底图样式源**：如果后面升级到矢量底图，OL 对 MVT 支持较弱（要靠 `ol/layer/VectorTile` + style 函数手写），而 maplibre 用 style.json。这一项建议编辑页继续用栅格底图，别追矢量。
4. **包体积**：两套都进主包会明显变大，必须按路由懒加载——`/gis/editor` 才加载 OL，`/gis/preview` 才加载 maplibre。
5. **学习/维护**：新人要会两套 API，出问题要判断属于哪套栈。

## 什么时候这套划分值得

**值得**，如果你确实存在这些需求：

- 编辑页要接 WMS/WFS/ArcGIS 服务做底图或参考图层；
- 需要按 CGCS2000 高斯投影精确量算、套合测绘成果；
- 需要强吸附（Snap）、多图层捕捉、复杂拓扑校验；
- 预览页要做矢量底图 + 三维地形 + 动画飞行。

**不值得**，如果编辑只是「在底图上画点线面、拖顶点、存进要素表」——那用 maplibre + terra-draw 一套栈就够，OL 的收益抵不过双栈成本。

按你描述的目标（AI 路线规划 + 地图编辑），我判断是**偏值得**的：路线编辑通常伴随吸附到路网、吸附到已有业务线，这是 OL 的强项；预览页要好看、要地形，是 maplibre 的强项。
